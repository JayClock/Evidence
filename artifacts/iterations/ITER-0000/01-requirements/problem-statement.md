# 问题陈述

## 背景

Evidence 是一个领域建模与证据映射平台，当前项目已经具备三类运行界面：React + Vite Web 前端、Rust Axum 后端，以及复用同一前端的 Tauri 2 桌面壳。后端围绕 User、Workspace、Member、Diagram、DiagramNode、DiagramEdge、LogicalEntity 等聚合提供 HAL 风格 REST API，并通过 SeaORM/PostgreSQL 与 fake store 契约测试保证核心领域行为一致。

当前产品的核心价值是帮助团队将业务领域中的证据、参与者、角色和上下文结构化，并通过图表达它们之间的关系。

## 核心问题

团队在进行领域建模、证据梳理和业务关系分析时，常见问题是：

- 业务概念散落在文档、会议和个人经验中，缺少统一语言。
- 证据材料与参与方、上下文、角色之间的关系难以可视化表达。
- 领域模型、图示表达和后续开发任务之间缺少可追溯链路。
- Web 与 Desktop 需要保持同一产品语义，但容易在实现和交付中分裂。
- 当前项目已经有领域聚合和 API 基础，但仍需要围绕真实用户流程补齐需求、建模、架构和计划工件。

## 机会陈述

如果 Evidence 能够提供一个围绕工作区、逻辑实体和关系图的统一建模体验，团队就可以在同一套工具中：

- 定义 Evidence、Participant、Role、Context 等核心领域概念。
- 通过 Diagram、Node、Edge 可视化表达业务关系。
- 将领域建模结果沉淀为可审计、可演进的产品工件。
- 让 Web 与 Desktop 共享同一前端、API 和领域语义。
- 将需求、领域模型、架构、计划、编码和评审串成连续工作流。

## 目标用户问题

### 领域建模负责人

如何快速建立一套团队都能理解和维护的领域模型，并持续追踪模型变化？

### 业务分析师 / 证据映射分析师

如何把合同、请求、确认、提案等业务证据与参与方、角色、上下文关联起来，并用图表达？

### 产品 / 交付团队成员

如何基于同一套领域模型理解需求范围、接口边界和后续实现任务？

### 桌面本地建模用户

如何在本地桌面环境中获得与 Web 一致的建模体验，方便演示和离线优先开发？

## 成功指标

| 维度       | 指标                                                    |
| ---------- | ------------------------------------------------------- |
| 模型表达   | 用户可以创建逻辑实体，并将其放入图中形成节点和关系      |
| 协作理解   | 团队能围绕统一语言和图结构讨论领域问题                  |
| API 一致性 | Web 与 Desktop 使用同一 REST API 语义和前端实现         |
| 可追溯性   | 需求、领域模型、架构、计划和代码增量均有 artifacts 记录 |
| 质量保障   | 核心领域行为有 fake store 与 PostgreSQL 契约测试保护    |

## 非目标

- 不在当前阶段引入独立于 `apps/web` 的第二套桌面前端。
- 不在需求阶段重写现有 Rust Axum 后端架构。
- 不把 Evidence 简化成通用白板工具；核心仍是领域建模和证据映射。
