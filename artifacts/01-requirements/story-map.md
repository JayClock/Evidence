# 用户故事地图

本文将 Evidence 的需求按用户活动、用户任务和可交付故事组织，用于后续领域建模、架构设计和 Sprint 计划。

## 用户活动主干

| 顺序 | 用户活动                  | 目标                                                 |
| ---- | ------------------------- | ---------------------------------------------------- |
| 1    | 进入工作区                | 让用户从默认用户或指定用户进入可协作的建模空间       |
| 2    | 管理逻辑实体              | 定义 Evidence、Participant、Role、Context 等业务概念 |
| 3    | 构建关系图                | 通过节点和边表达逻辑实体之间的业务关系               |
| 4    | 浏览和评审模型            | 让团队查看、讨论并校正领域模型                       |
| 5    | 保持 Web/Desktop 一致体验 | 让同一前端在浏览器和桌面壳中运行                     |
| 6    | 保障模型行为质量          | 通过契约测试确保 fake store 和 PostgreSQL 行为一致   |

## Release 1 故事地图

### 活动 1：进入工作区

| 用户故事 ID | 用户故事                                                         | 优先级 | 验收标准                                                                                             |
| ----------- | ---------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------- |
| US-001      | 作为用户，我希望能通过默认用户进入默认工作区，以便立即开始建模。 | P0     | API 根资源提供 default-user 链接；默认用户存在；默认用户拥有 default-workspace；返回 HAL `_links`。  |
| US-002      | 作为用户，我希望查看我的工作区列表，以便选择要建模的上下文。     | P0     | `GET /api/users/{userId}/workspaces` 返回分页集合；包含 `_embedded` 工作区；支持 page/pageSize。     |
| US-003      | 作为用户，我希望创建新的工作区，以便为不同业务领域隔离模型。     | P1     | `POST /api/users/{userId}/workspaces` 创建工作区；创建者自动成为 owner；重复或非法输入返回明确错误。 |

### 活动 2：管理逻辑实体

| 用户故事 ID | 用户故事                                                             | 优先级 | 验收标准                                                                                                     |
| ----------- | -------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------------------------------ |
| US-004      | 作为领域建模负责人，我希望创建逻辑实体，以便记录业务概念及其定义。   | P0     | 支持创建 Evidence、Participant、Role、Context 类型；支持子类型、定义、属性、行为、标签；返回实体 self 链接。 |
| US-005      | 作为业务分析师，我希望编辑逻辑实体，以便持续修正证据和上下文定义。   | P0     | `PUT /api/workspaces/{id}/logical-entities/{eid}` 可更新描述字段；不存在实体返回 NotFound。                  |
| US-006      | 作为团队成员，我希望查看工作区内所有逻辑实体，以便理解当前模型范围。 | P0     | 列表接口支持分页；返回 HAL 集合；实体类型和子类型清晰可见。                                                  |
| US-007      | 作为领域建模负责人，我希望删除不再使用的逻辑实体，以便保持模型干净。 | P1     | 删除采用现有软删除约定；后续列表不再显示；关联图节点的处理规则需明确。                                       |

### 活动 3：构建关系图

| 用户故事 ID | 用户故事                                                         | 优先级 | 验收标准                                                                                             |
| ----------- | ---------------------------------------------------------------- | ------ | ---------------------------------------------------------------------------------------------------- |
| US-008      | 作为用户，我希望创建图，以便围绕某个业务问题组织实体关系。       | P0     | `POST /api/workspaces/{id}/diagrams` 创建图；图属于工作区；返回 HAL 链接。                           |
| US-009      | 作为用户，我希望把逻辑实体添加为图节点，以便在图上表达业务概念。 | P0     | 创建节点时可引用 logical entity；节点包含类型、位置、样式；引用不存在时返回 Validation 或 NotFound。 |
| US-010      | 作为用户，我希望连接两个节点形成图边，以便表达关系类型和说明。   | P0     | 创建边时校验 source/target 节点存在；边包含 relation type 和 label；返回可追踪资源。                 |
| US-011      | 作为用户，我希望打开图时同时看到节点和边，以便完整理解模型。     | P0     | `GET /api/workspaces/{id}/diagrams/{did}` 返回图详情，并内嵌 nodes 和 edges。                        |

### 活动 4：浏览和评审模型

| 用户故事 ID | 用户故事                                                                           | 优先级 | 验收标准                                                                             |
| ----------- | ---------------------------------------------------------------------------------- | ------ | ------------------------------------------------------------------------------------ |
| US-012      | 作为团队成员，我希望查看逻辑实体详情，以便理解定义、属性和行为。                   | P1     | 实体详情包含 identity、description、类型、子类型、属性、行为、标签和 HAL 链接。      |
| US-013      | 作为评审参与者，我希望通过图查看证据、参与者、角色和上下文关系，以便发现模型缺口。 | P1     | 前端能渲染图节点和边；节点可区分实体类型；边标签可见。                               |
| US-014      | 作为领域建模负责人，我希望模型变更有清晰错误反馈，以便快速修复非法关系或缺失字段。 | P1     | API 将 Validation、Conflict、NotFound、Internal 映射为明确响应；前端展示可理解错误。 |

### 活动 6：保障模型行为质量

| 用户故事 ID | 用户故事                                                                         | 优先级 | 验收标准                                                                                                    |
| ----------- | -------------------------------------------------------------------------------- | ------ | ----------------------------------------------------------------------------------------------------------- |
| US-017      | 作为开发者，我希望 fake store 和 PostgreSQL 共享契约测试，以便确保领域行为一致。 | P0     | 工作区、成员、逻辑实体 CRUD 等关键行为在 fake store 和 PostgreSQL 实现中语义一致。                          |

## MVP 切片

### MVP-1：工作区与逻辑实体基础闭环

包含：US-001、US-002、US-004、US-005、US-006、US-017。

目标：用户能进入工作区，维护逻辑实体，并通过契约测试保护核心行为。

### MVP-2：图建模闭环

包含：US-008、US-009、US-010、US-011、US-013。

目标：用户能创建图，将逻辑实体放入图中，并通过边表达业务关系。

### MVP-3：桌面一致性与交付体验

包含：US-015、US-016、US-018。

目标：确保 Web/Desktop 共享体验，开发者能稳定构建、测试和扩展。

## 后续规划输入

建议 Sprint 1 聚焦 MVP-1，优先验证工作区与逻辑实体的端到端体验，并将现有 contract tests 作为 Definition of Done 的核心质量门槛。
