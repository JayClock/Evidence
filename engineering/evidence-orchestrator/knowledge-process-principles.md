# Evidence 知识过程原则

本文件记录团队采用的工程原则，不复制外部课程正文，也不把课程材料作为项目运行时输入。项目事实仍由 GitHub Issue、`docs/`、`.evidence/`、`contracts/`、源码与可执行测试共同承载。

## 原则

1. **围绕未知构造反馈循环**：阶段完成不是目标；每一步都要让业务、模型或实现中的关键未知更早暴露。
2. **一次处理一个最小问题**：一个 iteration 只激活一张 Story；编码时只激活该 Story 的一个可验收场景。
3. **TQA 提取隐性知识**：先说明当前 Thought，再向领域专家提出一个高价值、非技术 Question；Answer 必须来自领域专家，不由 Agent 推测。
4. **示例是业务反馈接口**：具体 Given/When/Then 用于确认理解，而不是在理解完成后补写的文档。
5. **模型必须能展开场景**：领域模型以解释示例中的事实、行为、关系、不变量和时间线为检验；不能展开时继续建模，而不是带着空洞模型进入编码。
6. **建模与检查相互独立**：Modeler 提议最小模型变化，Model Checker 只根据示例和模型寻找反例、歧义与遗漏；二者形成短循环。
7. **按功能上下文设计测试**：先确定业务可观察的 Q2，再以 Q1 定位领域、组件和适配器行为；测试替身服务于边界，不替代边界知识。
8. **TDD 的 Red 必须有语义**：只有聚焦测试因尚未实现的预期业务行为失败才是 Red；依赖、编译、配置和环境错误均不算 Red。
9. **机器事实只记录一次**：命令、退出码、哈希和时间以追加式执行日志为事实来源；Markdown 报告从日志和权威工件生成，不手工复制。
10. **人工反馈集中在价值判断**：人类在 Kickoff 选择问题、在模型 walkthrough/desk check 判断业务解释、在 Showcase 判断可运行增量；确定性格式检查交给工具。
11. **学习必须改变下一次行动**：Learn 记录 Probe、Sense、Respond；没有进入权威知识或下一问题的总结不构成学习闭环。

## 启发来源

- 徐昊，《AI 时代的软件工程》，极客时间：知识过程、TQA、模型反馈循环、测试策略、测试工序与测试驱动 AI 开发。
- 徐昊，《如何落地业务建模》，极客时间：统一语言、事件流、模型展开、REST 映射与 8X Flow。

这些来源只用于说明方法启发。仓库不保存课程全文；任何项目决策必须在本文件、架构决策或代码/测试中独立表达。
