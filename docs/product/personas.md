# Evidence 产品用户画像

本文件只描述 Evidence 建模平台的产品用户，不描述开发该平台的内部研发角色。候选变更应引用相关画像，不复制整份画像。

## 领域建模负责人

- **目标**：建立可视化领域模型，让团队围绕统一语言、业务证据和关系协作。
- **痛点**：知识散落在文档、会议和个人经验中，缺少可追踪的模型表达。
- **关键活动**：维护逻辑实体和关系、构建图、评审模型、修正概念边界。
- **成功标准**：实体、关系和上下文含义清晰，模型可以持续演进并解释真实业务场景。

## 业务分析师 / 证据映射分析师

- **目标**：把合同、请求、确认、提案等材料组织成结构化证据网络。
- **痛点**：证据的来源、责任方、上下文和约束关系难以追踪。
- **关键活动**：维护 Evidence、Participant、Role、Context，并表达它们之间的关系。
- **成功标准**：能够回答“什么证据由谁产生、服务哪个上下文、证明什么业务事实”。

## 交付输入整理者

- **目标**：把访谈、Issue、合同片段和手工记录保存为可追溯来源，供后续建模或交付确认使用。
- **痛点**：来源会反复更新或重试同步，难以判断哪一版被评审、是否重复以及当前处理状态。
- **关键活动**：捕获 Inbox 来源、查看不可变 Revision、核对来源 URI/metadata、延后或关闭条目。
- **成功标准**：同一来源可幂等同步，每个不同快照可按哈希追踪，后续决定能引用精确 Revision。

## 交付确认者

- **目标**：把有来源依据的交付建议提升为明确、可复现的 Story 输入。
- **痛点**：自动提议容易被误当成已批准需求，后续执行也可能引用错来源版本。
- **关键活动**：核对 Candidate 的角色、问题、目标、价值、认知模式与精确 Inbox 引用，明确确认或拒绝。
- **成功标准**：只有确认动作创建不可变 Story Revision v1；重试不重复创建，拒绝保留决定但不产生 Story。

## 桌面建模用户

- **目标**：通过桌面壳使用与 Web 一致的建模能力和本地 AI Agent。
- **痛点**：Web 与 Desktop 容易产生语义分裂，桌面连接的服务端边界不够清晰。
- **关键活动**：通过 Electron 壳使用共享 Web 前端、本地建模 Agent 和配置的 Server API。
- **成功标准**：桌面与 Web 共享产品语义、前端源码、权威服务端数据和 REST 领域语义。
